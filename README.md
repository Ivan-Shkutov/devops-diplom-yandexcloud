### Цели:
```
1. Подготовить облачную инфраструктуру на базе облачного провайдера Яндекс.Облако.
2. Запустить и сконфигурировать Kubernetes кластер.
3. Установить и настроить систему мониторинга.
4. Настроить и автоматизировать сборку тестового приложения с использованием Docker-контейнеров.
5. Настроить CI для автоматической сборки и тестирования.
6. Настроить CD для автоматического развёртывания приложения.
```
### Этапы выполнения:
```
1. Создание облачной инфраструктуры
2. Для начала необходимо подготовить облачную инфраструктуру в ЯО при помощи Terraform.
```
### Особенности выполнения:
```
1. Бюджет купона ограничен, что следует иметь в виду при проектировании инфраструктуры и использовании ресурсов; Для облачного k8s используйте региональный мастер(неотказоустойчивый). Для self-hosted k8s минимизируйте ресурсы ВМ и долю ЦПУ. В обоих вариантах используйте прерываемые ВМ для worker nodes.

2. Предварительная подготовка к установке и запуску Kubernetes кластера.

    1. Создайте сервисный аккаунт, который будет в дальнейшем использоваться Terraform для работы с инфраструктурой с необходимыми и достаточными правами. Не стоит использовать права суперпользователя

    2. Подготовьте backend для Terraform:
        а. Рекомендуемый вариант: S3 bucket в созданном ЯО аккаунте(создание бакета через TF) 
        б. Альтернативный вариант: Terraform Cloud

    3. Создайте конфигурацию Terrafrom, используя созданный бакет ранее как бекенд для хранения стейт файла. Конфигурации Terraform для создания сервисного аккаунта и бакета и основной инфраструктуры следует сохранить в разных папках.

    4. Создайте VPC с подсетями в разных зонах доступности.

    5. Убедитесь, что теперь вы можете выполнить команды terraform destroy и terraform apply без дополнительных ручных действий.

    6. В случае использования Terraform Cloud в качестве backend убедитесь, что применение изменений успешно проходит, используя web-интерфейс Terraform cloud.
```
### Ожидаемые результаты:
```
1. Terraform сконфигурирован и создание инфраструктуры посредством Terraform возможно без дополнительных ручных действий, стейт основной конфигурации сохраняется в бакете или Terraform Cloud

2. Полученная конфигурация инфраструктуры является предварительной, поэтому в ходе дальнейшего выполнения задания возможны изменения.

3. Создание Kubernetes кластера

4. На этом этапе необходимо создать Kubernetes кластер на базе предварительно созданной инфраструктуры. Требуется обеспечить доступ к ресурсам из Интернета.
Это можно сделать двумя способами:

    1. Рекомендуемый вариант: самостоятельная установка Kubernetes кластера.
        а. При помощи Terraform подготовить как минимум 3 виртуальных машины Compute Cloud для создания Kubernetes-кластера. Тип виртуальной машины следует выбрать самостоятельно с учётом требовании к производительности и стоимости. Если в дальнейшем поймете, что необходимо сменить тип инстанса, используйте Terraform для внесения изменений.
        б. Подготовить ansible конфигурации, можно воспользоваться, например Kubespray
        в. Задеплоить Kubernetes на подготовленные ранее инстансы, в случае нехватки каких-либо ресурсов вы всегда можете создать их при помощи Terraform.

    2. Альтернативный вариант: воспользуйтесь сервисом Yandex Managed Service for Kubernetes
        а. С помощью terraform resource для kubernetes создать региональный мастер kubernetes с размещением нод в разных 3 подсетях
        б. С помощью terraform resource для kubernetes node group
```
### Ожидаемый результат:
```
1. Работоспособный Kubernetes кластер.

2. В файле ~/.kube/config находятся данные для доступа к кластеру.

3. Команда kubectl get pods --all-namespaces отрабатывает без ошибок.

4. Создание тестового приложения

5. Для перехода к следующему этапу необходимо подготовить тестовое приложение, эмулирующее основное приложение разрабатываемое вашей компанией.
```
### Способ подготовки:
```
1. Рекомендуемый вариант:
    а. Создайте отдельный git репозиторий с простым nginx конфигом, который будет отдавать статические данные.
    б. Подготовьте Dockerfile для создания образа приложения.

2. Альтернативный вариант:
    а. Используйте любой другой код, главное, чтобы был самостоятельно создан Dockerfile.
```
### Ожидаемый результат:
```
1. Git репозиторий с тестовым приложением и Dockerfile.

2. Регистри с собранным docker image. В качестве регистри может быть DockerHub или Yandex Container Registry, созданный также с помощью terraform.

3. Подготовка cистемы мониторинга и деплой приложения

4. Уже должны быть готовы конфигурации для автоматического создания облачной инфраструктуры и поднятия Kubernetes кластера.

5. Теперь необходимо подготовить конфигурационные файлы для настройки нашего Kubernetes кластера.
```

### Цель:
```
1. Задеплоить в кластер prometheus, grafana, alertmanager, экспортер основных метрик Kubernetes.

2. Задеплоить тестовое приложение, например, nginx сервер отдающий статическую страницу.
```

### Способ выполнения:
```
1. Воспользоваться пакетом kube-prometheus, который уже включает в себя Kubernetes оператор для grafana, prometheus, alertmanager и node_exporter. 

2. Альтернативный вариант - использовать набор helm чартов от bitnami.

3. Деплой инфраструктуры в terraform pipeline

4. Если на первом этапе вы не воспользовались Terraform Cloud, то задеплойте и настройте в кластере atlantis для отслеживания изменений инфраструктуры. 

5. Альтернативный вариант 3 задания: вместо Terraform Cloud или atlantis настройте на автоматический запуск и применение конфигурации terraform из вашего git-репозитория в выбранной вами CI-CD системе при любом комите в main ветку. Предоставьте скриншоты работы пайплайна из CI/CD системы.
```
### Ожидаемый результат:
```
1. Git репозиторий с конфигурационными файлами для настройки Kubernetes.

2. Http доступ на 80 порту к web интерфейсу grafana.

3. Дашборды в grafana отображающие состояние Kubernetes кластера.

4. Http доступ на 80 порту к тестовому приложению.

5. Atlantis или terraform cloud или ci/cd-terraform

6. Установка и настройка CI/CD

7. Осталось настроить ci/cd систему для автоматической сборки docker image и деплоя приложения при изменении кода.
```
### Цель:
```
1. Автоматическая сборка docker образа при коммите в репозиторий с тестовым приложением.

2. Автоматический деплой нового docker образа.

3. Можно использовать teamcity, jenkins, GitLab CI или GitHub Actions.
```
### Ожидаемый результат:
```
1. Интерфейс ci/cd сервиса доступен по http.

2. При любом коммите в репозиторие с тестовым приложением происходит сборка и отправка в регистр Docker образа.

3. При создании тега (например, v1.0.0) происходит сборка и отправка с соответствующим label в регистри, а также деплой соответствующего Docker образа в кластер Kubernetes.
```
### Что необходимо для сдачи задания?
```
1. Репозиторий с конфигурационными файлами Terraform и готовность продемонстрировать создание всех ресурсов с нуля.

2. Пример pull request с комментариями созданными atlantis'ом или снимки экрана из Terraform Cloud или вашего CI-CD-terraform pipeline.

3. Репозиторий с конфигурацией ansible, если был выбран способ создания Kubernetes кластера при помощи ansible.

4. Репозиторий с Dockerfile тестового приложения и ссылка на собранный docker image.

5. Репозиторий с конфигурацией Kubernetes кластера.

6. Ссылка на тестовое приложение и веб интерфейс Grafana с данными доступа.

7. Все репозитории рекомендуется хранить на одном ресурсе (github, gitlab)
```

### <u>1.	Создание облачной инфраструктуры</u>

#### Этап 1: Создание инфраструктуры в Yandex Cloud с использованием Terraform

1.	Цель этапа:

Целью данного этапа является первичная подготовка облачной среды в Yandex Cloud для дальнейшего развертывания инфраструктуры с использованием Terraform.

```
В рамках этапа необходимо:
-	создать сервисный аккаунт для Terraform 
-	настроить минимально необходимые права доступа 
-	организовать безопасный способ аутентификации Terraform 
-	подготовить основу для дальнейшего развертывания инфраструктуры
```

2.	Используемые инструменты:

```
В процессе выполнения этапа использовались следующие инструменты:
-	Terraform v1.14.8 — инструмент управления инфраструктурой как кодом (IaC) 
-	Yandex Cloud CLI (yc v0.199.0) — инструмент управления облаком 
-	Yandex Cloud IAM — система управления доступом 
```

![1](https://github.com/Ivan-Shkutov/devops-diplom-yandexcloud/blob/main/png/1.png)

3.  Описание реализованной инфраструктуры

    3.1.    Структура Terraform конфигурации

На данном этапе использовалась структура проекта:

```
infra/
└── 01-bootstrap/
	├── main.tf        	# конфигурация провайдера Yandex Cloud
	├── variables.tf   	# переменные (cloud_id, folder_id, token)
	├── sa.tf          	# сервисный аккаунт
	├── roles.tf       	# IAM роли
	├── key.tf         	# ключ доступа (static access key)
	└── outputs.tf     	# выходные значения
```    
    3.2.    Сервисный аккаунт

В Yandex Cloud был создан сервисный аккаунт:
```
-	Имя: terraform-sa 
-	Назначение: автоматизация управления инфраструктурой через Terraform 
Данный аккаунт используется для выполнения операций создания, изменения и удаления облачных ресурсов.
```

![2](https://github.com/Ivan-Shkutov/devops-diplom-yandexcloud/blob/main/png/2.png)


    3.3.    Назначение ролей (IAM)

Сервисному аккаунту были назначены минимально необходимые роли для будущей работы с инфраструктурой:
```
-	storage.admin — управление Object Storage 
-	vpc.admin — управление виртуальными сетями 
-	compute.admin — управление виртуальными машинами 
-	k8s.admin — управление Kubernetes-кластерами 
Применён принцип минимально необходимых привилегий (Least Privilege), что повышает безопасность инфраструктуры.
```

![4](https://github.com/Ivan-Shkutov/devops-diplom-yandexcloud/blob/main/png/4.png)

    3.4.    Аутентификация Terraform

Для взаимодействия Terraform с Yandex Cloud была настроена аутентификация через:

        - YC CLI (user token authentication) 

Получение токена выполняется командой:

        - yc iam create-token

Данный токен используется Terraform для выполнения операций в облаке.

    3.5.    Конфигурация Terraform провайдера

Terraform был настроен на работу с Yandex Cloud через официальный провайдер:  

        - yandex-cloud/yandex 

Аутентификация выполняется с использованием токена пользователя Yandex Cloud.

    3.6.    Выходные данные (Outputs)

После выполнения Terraform предоставляются следующие значения:

```
-	access_key — ключ доступа для сервисного аккаунта 
-	secret_key — секретный ключ 
Эти данные могут использоваться для дальнейшей настройки backend хранения состояния Terraform.
```

![3](https://github.com/Ivan-Shkutov/devops-diplom-yandexcloud/blob/main/png/3.png)


4.  Результаты выполнения этапа

В результате выполнения этапа 01-bootstrap были достигнуты следующие результаты:

```
-	создан сервисный аккаунт terraform-sa
-	настроены IAM роли с минимально необходимыми правами
-	настроена аутентификация Terraform через YC CLI
-	создан static access key для сервисного аккаунта
-	подготовлена базовая структура Terraform проекта
-	получены ключи доступа для дальнейшей работы
```

5.  Важные архитектурные решения:

```
Использование service account позволяет:
•	автоматизировать управление инфраструктурой 
•	исключить использование персональных учетных записей 
•	повысить безопасность и управляемость 
-	принцип минимальных прав
-	назначены только необходимые роли, что снижает потенциальные риски безопасности

Использование Terraform как основной инструмент Infrastructure as Code, обеспечивающий:
-	воспроизводимость инфраструктуры 
-	версионирование конфигурации 
-	автоматизацию развертывания 
```

6.  Вывод по этапу:

В результате создана базовая среда управления облачными ресурсами в Yandex Cloud, включающая сервисный аккаунт, IAM-права и механизм аутентификации Terraform.

Данная основа является фундаментом для дальнейшего построения сетевой инфраструктуры (VPC), Kubernetes-кластера и CI/CD процессов.



#### Этап 2: Создание сетевой инфраструктуры и настройка Terraform backend в Yandex Cloud

1.	Цель этапа

Целью данного этапа являлось создание базовой сетевой инфраструктуры в Yandex Cloud и настройка централизованного хранения состояния Terraform (remote backend) с использованием S3-совместимого Object Storage.

В рамках этапа необходимо:
```
-	настроить удалённое хранение состояния Terraform (backend); 
-	создать виртуальную сеть (VPC); 
-	создать подсети в разных зонах доступности; 
-	подготовить сетевую инфраструктуру для последующего развертывания Kubernetes-кластера. 
```

2.  Используемые инструменты

В процессе выполнения этапа использовались следующие инструменты:
```
-	Terraform v1.14.8 — инструмент IaC 
-	Yandex Cloud CLI (yc v0.199.0) — управление облаком 
-	Yandex Cloud Object Storage — хранение Terraform state (S3 backend) 
-	Yandex Virtual Private Cloud (VPC) — создание сети и подсетей 
```

3.  Описание реализованной инфраструктуры 

    3.1.    Структура Terraform конфигурации

```
infra/
└── 02-network
 	 ├── backend.tf   	# удалённое хранение state
   	 ├── provider.tf   	# настройка провайдера Yandex Cloud
   	 ├── variables.tf  	# переменные Terraform
   	 ├── network.tf    # VPC сеть
   	 └── subnets.tf     # подсети
```

    3.2.    Выбор backend

Для хранения состояния Terraform был выбран:

-	Yandex Object Storage (S3-compatible backend)

Это обеспечивает:
```
-	централизованное хранение состояния инфраструктуры 
-	защиту от потери state-файла 
-	возможность командной работы 
-	интеграцию с CI/CD системами 
```

    3.3.    Конфигурация backend

Backend был настроен в файле backend.tf:
```
-	используется S3-совместимый интерфейс Yandex Cloud Storage 
-	указаны access_key и secret_key сервисного аккаунта 
-	задан отдельный ключ состояния (key) для логического разделения инфраструктуры 
```

    3.4.    Особенности конфигурации

При настройке backend были учтены особенности Yandex Cloud:
```
-	использование параметра endpoints.s3 
-	отключение проверки AWS-специфичных параметров: 
        skip_region_validation 
        skip_credentials_validation 
        skip_requesting_account_id 
        skip_s3_checksum 
```

4.  Сетевая инфраструктура (VPC)

    4.1.    Создание виртуальной сети

Была создана виртуальная частная сеть. Данная сеть является основой всей будущей инфраструктуры.

    - имя: main-network

    5.2.    Переменные

Используются следующие переменные:
```

```
    5.3.    Основные ресурсы

В рамках этапа создаются:
```
- yandex_vpc_network 
- yandex_vpc_subnet 
```

В результате выполнения этапа была создана базовая сетевая инфраструктура:

-	настроен Terraform backend на базе S3 (Object Storage)
-	создана виртуальная сеть (VPC)
-	созданы подсети в двух зонах доступности
-	подготовлена основа для Kubernetes-кластера

```

7. 	Важные архитектурные решения

```
Применение S3 backend позволяет:
- избежать потери состояния инфраструктуры; 
- упростить совместную работу; 
- обеспечить возможность CI/CD интеграции. 
Создание подсетей в разных зонах доступности обеспечивает:
- основу для отказоустойчивой архитектуры; 
- возможность распределения нагрузки; 
- подготовку к кластеру Kubernetes. 
Вся инфраструктура описана декларативно с использованием Terraform, что обеспечивает:

2.  Создание инфраструктуры (Terraform)

Организуем Terraform-проекты по этапам и отдельным директориям:

```
infra/
└── 03-k8s/
	├── bastion.tf    	 	# конфигурация провайдера Yandex Cloud
	├── k8s-vm.tf   		# переменные (cloud_id, folder_id, token)
	├── network.tf         	# сервисный аккаунт
	├── outputs.tf       	# выходные значения
	├── provider.tf        	# ключ доступа (static access key)
	├── security.tf     	# конфигурация провайдера Yandex Cloud
	├── variables.tf   		# переменные (cloud_id, folder_id, token)
	├── terraform.tfvars   	# сервисный аккаунт
	└── terraform.tfstate  	# выходные значения
```    

```
infra/
    ├── 01-bootstrap/   # например, создание учетных записей, ключей, S3 бакета для state
    ├── 02-network/     # сеть: VPC, подсети, NAT, gateway
    └── 03-k8s/         # виртуальные машины + bastion под кластер Kubernetes
```

Каждый каталог содержит свои `\*.tf`-файлы. Такой подход (мульти-модульная структура) — хорош, потому что инфраструктура разбита на смысловые части.

Развёртывание инфраструктуры

Переходим поочерёдно в каждый каталог и выполняем стандартный цикл Terraform:

    1.   Bootstrap:
```

   cd infra/01-bootstrap

   terraform apply     # создание ресурсов bootstrap
```

    2.  Сеть:
```
bash
   cd ../02-network
   terraform init
   terraform apply     # создаются VPC, подсети и т.д.
```

    3.  Kubernetes-виртуалки:
```
bash
   cd ../03-k8s
   terraform init
   terraform apply     # создаются VM: master-ноды и workers

`terraform init` Terraform инициализирует рабочую директорию и скачивает необходимые плагины. 

`terraform apply` применяет изменения (создаёт или обновляет ресурсы) согласно конфигурации. По умолчанию она спросит подтверждение перед изменениями; можно добавить `-auto-approve` для автоматического согласия.

    3.2.    Inventory

Сначала создаём Ansible inventory.ini. Обычно копируем `inventory/sample`:

```

cd infra/03-k8s/kubespray

```

master ansible_host=10.10.0.3

master

node1
node2
node3

kube_control_plane
kube_node
```

```
ansible-playbook -i inventory/mycluster/inventory.ini -u ubuntu cluster.yml --become
```

`-i` — мой инвентори.
`cluster.yml` — основной playbook Kubespray.
Флаг `-b` (become) повышает привилегии (используется sudo).

Kubespray установит Kubernetes (kubeadm), настроит сети, etcd и т.д.

4.  Ошибки и почему они были

- Ошибка 1: Ansible version
```
Ansible must be between 2.18.0 and 2.19.0
Причина:
Kubespray требует конкретную версию Ansible.
Решение:
Создание venv + установка нужной версии.
```
- Ошибка 2: IP mismatch (Kubespray bootstrap)
```
does not contain external IP
Причина:
Я указал public IP, но Ansible проверяет internal IP
Решение:
Inventory должен использовать internal IP (10.x.x.x)
```
- Ошибка 3: Kubernetes API localhost:8080
```
connection refused
Причина:
kubectl не видит kubeconfig
Решение:
mkdir -p ~/.kube
sudo cp /etc/kubernetes/admin.conf ~/.kube/config
sudo chown ubuntu:ubuntu ~/.kube/config
export KUBECONFIG=$HOME/.kube/config
```

### <u>4.	Подготовка cистемы мониторинга и деплой приложения</u>

1.	Цель этапа

В рамках этапа необходимо:
```
- развернуть Kubernetes кластер в облаке
- настроить систему мониторинга: Prometheus, Grafana, Alertmanager, Node Exporter
- задеплоить тестовое приложение (nginx)
- обеспечить доступ к сервисам через HTTP
- настроить инфраструктуру как код (Terraform + CI/CD)
```
2.  Система мониторинга

Рразвёртывание системы мониторинга. Используем готовый Helm-чарт (kube-prometheus-stack) от Prometheus Community. Он включает Prometheus Operator, Grafana, Alertmanager, node-exporter, kube-state-metrics и преднастроенные дашборды.

Можно действовать двумя способами:

    1.  Через Helm:

        - Добавляем репозиторий чартов Prometheus Community:
```
bash
     helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
     helm repo update
```
        - Создаём namespace:
```
bash
     kubectl create namespace monitoring
```
        - Устанавливаем kube-prometheus-stack с настройками по умолчанию:
```
bash
     helm install prometheus-stack prometheus-community/kube-prometheus-stack \\
       --namespace monitoring \\
       --create-namespace
```
     Эта команда развернёт все компоненты со стандартной конфигурацией.

   В дальнейшем можно настроить параметры (например - ресурсы, StorageClass и т.д.) через файл `values.yaml`.

    2.  Через манифесты (kube-prometheus repository):

        - Клонируем репозиторий с манифестами:
```
bash
     git clone https://github.com/prometheus-operator/kube-prometheus.git
     cd kube-prometheus
```
        - Применяем CRD и другие ресурсы:
```
bash
     kubectl apply --server-side -f manifests/setup
     kubectl apply -f manifests/
```
Этот способ описан в https://github.com/prometheus-operator/kube-prometheus#.

        - Проверка

     Убедимся, что в namespace `monitoring` запущены все поды:
```
bash
    kubectl get pods -n monitoring
```
Ожидаются поды `prometheus-\*`, `grafana-\*`, `alertmanager-\*`, `node-exporter-\*`, `kube-state-metrics-\*` и т.д. Их статус должен быть `Running`.

6.  Deploy В Kubernetes

Создаю манифесты Deployment и Service для моего nginx-приложения. Например, в `cicd/k8s/`:

deployment.yaml
```
yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
spec:
  replicas: 1
  selector:
    matchLabels:
      app: nginx-test
  template:
    metadata:
      labels:
        app: nginx-test
    spec:
      containers:
      - name: nginx-test
        image: YOUR\_DOCKERHUB/test-app:latest
        ports:
        - containerPort: 80
```

Deployment создаёт ReplicaSet и поды с nginx.

Указываю `image: youruser/test-app:latest`.

service.yaml
```
yaml
apiVersion: v1
kind: Service
metadata:
  name: nginx-service
spec:
  type: NodePort
  selector:
    app: nginx-test
  ports:
    - port: 80
      targetPort: 80
      nodePort: 30080
```

Service типа NodePort пробрасывает 80 порт сервиса на ноды кластера.

В данном примере NodePort = 30080 (выбрать свободный порт в диапазоне 30000–32767).

`selector` должен совпадать с `labels` подов (здесь `app: nginx-test`).

Деплой манифестов:
```
bash
kubectl apply -f cicd/k8s/deployment.yaml
kubectl apply -f cicd/k8s/service.yaml
```

Проверяем:
```
bash
kubectl get deployments
kubectl get pods
kubectl get svc
```

Убедитесь, что поды запущены. Затем откройте приложение:
```
http://<IP-адрес-любого-нод>:30080
```

Например, на одном из worker нод (в нашем случае порты 80 проброшены на 30080). Должна открыться статическая страница nginx.

### <u>5.	Установка и настройка CI/CD</u>


1.  Общая архитектура

Итоговая система состоит из следующих компонентов:
```
    1.  Облачная инфраструктура - Terraform создаём в облаке YC необходимые ресурсы:
        - VPC (сеть) и подсети;
        - Security groups / Firewall;
        - Виртуальные машины (VM) для мастер- и воркер-нод Kubernetes.
        - Kubernetes-кластер (Kubespray) на созданных ВМ разворачиваем кластер:
            - Master-ноды и worker-ноды;
            - Сеть Kubernetes (CNI, например Calico);
            - Ingress-контроллер.

    2.  Monitoring Stack - разворачиваем систему мониторинга через kube-prometheus-stack:
        - Prometheus (с оператором Prometheus Operator);
        - Grafana для визуализации метрик;
        - Alertmanager для оповещений;
        - Node-exporter для метрик нод и kube-state-metrics для метрик кластера.
        - CI/CD Pipeline (GitHub Actions)** – автоматизация сборки и деплоя приложения:

    3.  Сборка Docker-образа при коммитах;
        - Публикация образа в Docker Hub или другом регистре;
        - Деплой в Kubernetes (по SSH на master или с помощью ArgoCD и т.д.).

    4.  Тестовое приложение nginx:
        - Простой nginx-сервер, отдающий статическую HTML-страницу;
        - Образ в Docker Hub.
```

Таким образом, полностью автоматизированное решение будет включать: 

    - Terraform-конфигурации
    
    - Ansible/Kubespray для K8s
    
    - Helm или манифесты для мониторинга
    
    - CI/CD для сборки и деплоя
    
    - Тестовый nginx-сервис



2.  CI/CD pipeline GitHub Actions

Настроим GitHub Actions для автоматической сборки Docker-образа и деплоя в K8s.

![56](https://github.com/Ivan-Shkutov/devops-diplom-yandexcloud/blob/main/png/56.png)


Логика пайплайна:

```
GitHub push в ветку main или tag (например, v1.0.1)
   ↓
Собираем Docker-образ
   ↓
Публикуем его в Docker Hub
   ↓
(по тегу) — подключаемся по SSH к master-ноде
   ↓
Выполняем: kubectl set image
```
![61](https://github.com/Ivan-Shkutov/devops-diplom-yandexcloud/blob/main/png/61.png)


То есть, при каждом пуше в main: билдим и пушим образ с тэгом `latest`.  

При push tag вида `v\*`: build образа с этим тэгом, push и выполняем обновление deployment в кластере.

В этом yaml:

```
Build: при любом пуше в `main` происходит сборка и пуш latest-образа (steps `Build image`/`Push image`).

build\_tag:* при появлении тега `vX.Y.Z` GitHub передаёт его в `github.ref`, делается сборка и пуш образа с этим тэгом.

Deploy: также на теге, после успешной сборки, выполняется SSH кластера на мастер-ноду с помощью ssh-action и командами `kubectl set image` и `kubectl rollout status`.

Похожую логику CI/CD описывает официальная документация Docker для GitHub Actions. Они показывают, как логиниться в Docker Hub и пушить образы.
(https://docs.docker.com/guides/gha/)
 
 Важные моменты:

- Docker Hub: в workflows используем секреты `DOCKER\_USERNAME` и `DOCKER\_PASSWORD`. Docker-логины GitHub Actions выполняются через `docker/login-action`.

- Обновление деплоя: команда `kubectl set image deployment/NAME *` обновляет контейнер в деплойменте на новую версию. После этого `kubectl rollout status deployment/NAME` отслеживает завершение обновления.

- GitHub Secrets: в моем GitHub-репозитории нужно добавить секреты (Settings → Secrets \& Variables → Actions):
    - DOCKER\_USERNAME – логин от Docker Hub.
    - DOCKER\_PASSWORD – пароль/токен Docker Hub.
    - SSH\_HOST – IP или DNS мастер-ноды (куда ходит SSH).
    - SSH\_USER – пользователь на мастер-ноде.
    - SSH\_KEY – приватный SSH-ключ (вместе с authorized\_keys на сервере).
```


3. Порядок выполнения задания

 - При `push` в ветку `main` запускается джоб `build`: образ собирается и отправляется как `latest`.

 - При `push тега` (например, `v1.0.0`) выполняется `build\_tag` (образ с этим тэгом) и `deploy` (обновление Deployment в кластере).

Например:

```
git add . 
git commit -m "Первый comit"
git push origin main

git tag v1.0.1
git push origin v1.0.1
```

Проверить работу CI/CD можно по логам GitHub Actions и через веб-интерфейс. При успешном деплое новые поды приложения появятся в Kubernetes.

4. Итоговый результаты

**Terraform:** - инициализация `terraform init` и применение `terraform apply` создают облачную инфраструктуру.

**Тестовое приложение:** веб-страница nginx по URL `http://<IP-нод>:30080`.

**Docker Hub:** храним образы централизованно, чтобы Kubernetes и CI могли их тянуть.

**Kubespray:** - для простого развёртывания кластера через Ansible (inventory + ansible-playbook).

**Grafana:** открытая панель `http://<IP-мастера>:3000` (например, Node Exporter или Dashboard с состоянием кластера).

**Kubernetes Monitoring Stack:** - Prometheus собирает метрики из нод и API сервера, Grafana визуализирует, Alertmanager шлёт оповещения при проблемах.

**CI/CD интерфейс:** страницу GitHub Actions с прошедшими workflow.

Также проверил, что при обновлении кода выполняется автоматическая сборка и деплой. Например, при изменении  `index.html`, сделал push в main и создал тег и страница обновилась и в Grafana новая метрика или в Kubernetes новый под.

**CI/CD pipeline:** - автоматизация сборки и деплоя кода при коммитах.

**SSH на master:** - из GitHub Actions мы подключаемся к кластеру по SSH и вызываем kubectl.

**kubectl set image и `rollout`:** - Kubernetes обновляет приложения. `set image` меняет образ в Deployment, `kubectl rollout status` ждёт обновления.

**GitHub Secrets:** - защищаем пароли и токены.
